## Philosophy of WORK

### 1. **Coordination, Not Execution**

WORK **does not execute** code directly. Your role is:

- Grouping related PROCESSES
- Establishing collaboration policies
- Managing communication between PROCESSES
- Coordinating the start and end of workflows

### 2. **Composition of Complete Units**

Each PROCESS within a WORK is a complete unit:

- Has its own TASKS
- Manages its resources internally
- Maintains its isolation space
- Can be developed independently

### 3. **Systemic View**

The WORK provides an integrated view:

- Aggregate metrics of all PROCESSES
- Common QoS policies
- Shared resource limits
- Synchronization points between PROCESSES

```
WORK "ParallelProcessing"

## Types of WORK

### 1. **Sequential (Pipeline) WORK**

Processes execute sequentially, such as An assembly line:

```
WORK "VideoProcessing"

[Extract frames] → [Apply filters] → [Encode] → [Save]

PROCESS A PROCESS B PROCESS C PROCESS D
```

**Characteristics:**

- Output of one process is input of the next
- Bottleneck is the slowest process
- Limited parallelism

### 2. **Parallel WORK (Map-Reduce)**

Processes divide work and consolidate results:

```
WORK "LogAnalysis"
PROCESS_Divider

├── PROCESS_Analyzer1 (part of the logs)

├── PROCESS_Analyzer2 (part of the logs)

├── PROCESS_Analyzer3 (part of the logs)

└── PROCESS_Analyzer4 (part of the logs)

PROCESS_Consolidator (final result)
```

**Characteristics:**

- Independent partitioned work
- Horizontal scalability
- Reduction/aggregation phase

### 3. **Master-Slave WORK**

A coordinating process directs workers:

```
WORK "WebClusterServer"

PROCESS_LoadBalancer (master)

├── PROCESS_WebServer1 (slave)

├── PROCESS_WebServer2 (slave)

├── PROCESS_WebServer3 (slave)

└── PROCESS_WebServer4 (slave)
```

**Characteristics:**

- Centralized coordination
- Slaves are interchangeable
- Single point of failure (master)

### 4. **Cooperative WORK**

Processes collaborate without a rigid hierarchy:

```
WORK "P2P System"
PROCESS_Node1 ↔ PROCESS_Node2

↕ ↕

PROCESS_Node3 ↔ PROCESS_Node4
```

**Characteristics:**

- Any-to-any communication
- Dynamic discovery
- Distributed fault tolerance

### 5. **Composite WORK**

WORK that contains other WORKS (hierarchy of WORKS):

```
WORK "Enterprise System"

├── WORK "Frontend" (user interfaces)

│ ├── PROCESS "WebApp"

│ └── PROCESS "MobileAPI"
│
├── WORK "Backend" (business logic)
│ ├── PROCESS "CustomerService"

│ └── PROCESS "ProductService"

│
└── WORK "Data" (persistence)

├── PROCESS "MainDatabase"

└── PROCESS "Cache"

```

## Complete Example: Bank Transaction Processing WORK

```c
// WORK Definition
work_id_t wid_sistema_bancario = work_criar(
"SistemaBancario",
WORK_HIBRIDO, // Mixture of sequential and parallel
POLICICA_CONSISTENCIA_FORTE | POLICICA_AUDITORIA
);

/ // Creation of PROCESSES (simplified)
processo_id_t pid_web = processo_criar("InterfaceWeb", LIMITES_WEB);

processo_id_t pid_auth = processo_criar("Autenticacao", LIMITES_AUTH);

process_id_t pid_tx = process_create("ProcessorTx", LIMITS_TX);
process_id_t pid_notif = process_create("Notifications", LIMITS_NOTIF);
process_id_t pid_audit = process_create("Audit", LIMITS_AUDIT);

/ // Adds PROCESSES to WORK with their roles
work_add_process(wid_banking_system, pid_web, INTERFACE_ROLE, NULL);

work_add_process(wid_banking_system, pid_auth, VALIDATOR_ROLE, NULL);

work_add_process(wid_banking_system, pid_tx, MAIN_PROCESSOR_ROLE, NULL);
work_add_processo(wid_sistema_bancario, pid_notif, PAPEL_NOTIFICADOR, NULL);
work_add_processo(wid_sistema_bancario, pid_audit, PAPEL_AUDITOR, NULL);

// Configure dependencies
dependencies_t deps_auth = { .processos = {pid_web}, .quantos = 1 };
work_add_dependency(pid_auth, deps_auth);

dependencies_t deps_tx = { .processos = {pid_auth}, .quantos = 1 };
work_add_dependency(pid_tx, deps_tx);

dependencies_t deps_notif = { .processos = {pid_tx}, .quantos = 1 };
work_add_dependency(pid_notif, deps_notif);

// Configures communication channels
// Main channel: web → auth → tx → notif (data)
work_connect_processes(wid_banking_system, pid_web, pid_auth, DATA_CHANNEL, QoS_RELIABLE);

work_connect_processes(wid_banking_system, pid_auth, pid_tx, DATA_CHANNEL, QoS_RELIABLE);

work_connect_processes(wid_banking_system, pid_tx, pid_notif, DATA_CHANNEL, QoS_FAST);

// Audit channel: all → audit (events)
work_connect_processes(wid_banking_system, pid_web, pid_audit, EVENT_CHANNEL, QoS_RELIABLE);
work_connect_processes(wid_banking_system, pid_auth, pid_audit, EVENT_CHANNEL, QoS_RELIABLE);
work_connect_processes(wid_banking_system, pid_tx, pid_audit, EVENT_CHANNEL, QoS_RELIABLE);
work_connect_processes(wid_banking_system, pid_notif, pid_audit, EVENT_CHANNEL, QoS_RELIABLE);

/ Define shared limits
work_define_cpu_limit(wid_banking_system, 400); // 4 CPUs in total
work_definir_limite_memoria(wid_sistema_bancario, 8 * 1024 * 1024 * 1024); // 8GB total

// Starts the WORK
work_iniciar(wid_sistema_bancario);

/ Monitoring
while (work_estado(wid_sistema_bancario) == ATIVO) {

metricas_work_t m = work_metricas(wid_sistema_bancario);

printf("WORK: %s\n", m.nome);

printf(" Throughput: %llu tx/seg\n", m.throughput);

printf(" Average latency: %llu ms\n", m.latencia_media);

printf(" Error rate: %.2f%%\n", m.taxa_erro * 100);

printf(" CPU total: %d%%\n", m.cpu_percent);

if (m.error_rate > 0.01) {

work_rebalance(banking_system_wid); // Reacts to problems

}

wait_time(1000); // 1 second

}

// Coordinated finalization
work_finalize(banking_system_wid);

```

## Design Considerations

### When to Use WORK?

| Scenario | WORK Approach |

|---------|-------------------|

| **Microservices** | Each service is a PROCESS, the system is a WORK |

| **Data Pipeline** | Sequential WORK with staged processes |

| **Parallel Processing** | Parallel WORK with division of labor |

| **Distributed Systems** | WORK with processes on different machines |

| **Modular Applications** | Composite WORK with submodules |

### Best Practices

1. **Appropriate Granularity**

- Very small processes: excessive overhead

- Very large processes: rigidity, difficult reuse

2. **Explicit Dependencies**

- Clearly document dependencies

- Avoid circular dependencies

- Use interface versioning

3. **Monitoring I**Integrated**

- Collect metrics at all levels

- Correlate events between PROCESSES

- Detect systemic anomalies

4. **Fault Handling**

- Define recovery policies

- Isolate faults to specific PROCESSES

- Maintain WORK consistency

## Conclusion

The **WORK** completes the system hierarchy, representing the highest level of abstraction where entire PROCESSES collaborate towards common goals. While ACTIVITY, THREAD, TASK, and PROCESS deal with execution and resources, the WORK focuses on the **coordination and composition** of complete computational units.

This layered architecture provides:

- **ACTIVITY**: Atomic unit (what)
- **THREAD**: Activity executor (who executes)
- **TASK**: Thread container (execution context)
- **PROCESS**: Task container (administrative unit)
- **WORK**: Set of processes (complete system)

Each level adds semantic value and specific capabilities, allowing you to build complex systems in an organized, understandable, and manageable way.
