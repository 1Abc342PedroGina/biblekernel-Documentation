Overview
ACTIVITY represents the fundamental atomic unit of processing in the system. As a pure and self-contained concept, an ACTIVITY encapsulates a complete and indivisible computation, operating as a grain of execution that can be scheduled, distributed, and executed independently.

Atomic Model Philosophy
ACTIVITY is the smallest unit of processing with complete computational meaning. Unlike threads or traditional processes, ACTIVITY has no persistent state between executions - each instance is an atomic computation that executes until completion or failure.

ACTIVITY Architecture
1. Formal Definition
An ACTIVITY is defined as a triple:

text
ACTIVITY = (CODE, INPUT, OUTPUT)

Where:

CODE: Atomic sequence of instructions

INPUT: Immutable data for processing

OUTPUT: Result of the computation (produced only once)

2. Atomic Characteristics
Fundamental Properties:

Atomicity: Executes completely or does not execute

Immutability: Input cannot be altered during execution

Determinism: Same input produces same output

Independence: Does not share state with other ACTIVITIES

Transparency: Does not know the execution context

text
CREATION (instantiation with input)

↓
VALIDATION (integrity check)

↓
EXECUTION (atomic processing)

↓
FINALIZATION (output production)

↓ DESTRUCTION (resource release)
Lifecycle Rules:

No suspension or blocking

No waiting for external resources

No interaction with other ACTIVITIES

Output is produced exactly once

5. Formal Specification
c
// Abstract definition of an ACTIVITY
typedef struct activity {

/ Identification
uuid_t id; // Unique identifier

/ Computation metadata
activity_type_t type; // Classification
priority_t priority; // For scheduling

/ The computation itself
atomic_function_t function; // The code to execute
input_data_t input; // Input data (immutable)

/ Result
output_data_t output; // Where the result is stored

/ Guarantees
timeout_t maximum_time; // Maximum execution time
size_t maximum_memory; // Maximum allowed memory
} activity_t;

6. Detailed Atomic Properties
Indivisibility
An ACTIVITY cannot be partially executed:

c
// Execution is all-or-nothing
result_t activity_execute(activity_t *act) {

/ All or nothing

if (validate_input(act->input)) {
act->output = act->function(act->input);

return SUCCESS;

}
return FAILURE; // Nothing is produced
} Isolation
Each ACTIVITY operates in its own sandbox:

No access to external memory

No global side effects

No state dependencies

No direct communication

7. Composition of ACTIVITIES
ACTIVITIES can be composed into workflows without losing atomicity:

c
// Sequential composition (each one atomic)
workflow_t workflow = {

.activities = {

{ .type = READ_SENSOR, .input = "temp1" },

{ .type = CALCULATE_AVERAGE, .input = "$0.output" },

{ .type = STORE_RESULT, .input = "$1.output" }

}
};

// The workflow manages the threading,

// but each ACTIVITY maintains its atomicity
8. Execution Guarantees
Progress Guarantee
An ACTIVITY always progresses until completion or failure:

No deadlocks (no waiting)

No starvation (fair scheduling)

No race conditions (no sharing)

Isolation Guarantee
Failures in one ACTIVITY do not affect others

Memory leaks are contained

Divergent computations are timed out

11. Advantages of the Atomic Model
Conceptual Simplicity: An ACTIVITY is a black box that transforms input into output

Reliability: Atomicity guarantees consistency

Scalability: Activities can be distributed without coordination

Testability: Each activity is testable in isolation

Observability: Clear state (running/completed/failed)

Recovery: Failures are contained within the individual activity

12. Limitations and Considerations
Granularity: Very small activities generate overhead

Communication: Activities do not communicate directly

State: Stateful computations need to be refactored

Real-Time: Timeouts are crucial to guarantee atomicity

13. Advanced Example: Activity Pipeline
c
// Transaction processing system
typedef struct pipeline {

activity_t validate; // Validates format

activity_t process; // Processes transaction

activity_t persist; // Saves result

activity_t notify; // Notifies client
} pipeline_transaction_t;

/ // Usage
transaction_t tx = receive_transaction();

/ // Each activity is executed atomically
if (activity_execute(&pipeline.validate, tx)) {
result_t res = activity_execute(&pipeline.process, tx);
activity_execute(&pipeline.persist, res);
activity_execute(&pipeline.notify, res);

Conclusion
The ACTIVITY as an atomic unit represents a powerful abstraction that drastically simplifies the development of concurrent and distributed systems. By eliminating shared state and direct communication, the atomic model allows building more reliable, testable, and scalable systems, where each unit of computation is an isolated island that transforms immutable inputs into deterministic outputs.

This model is particularly suitable for:

Stream data processing

Microservices and serverless

Parallel and distributed computing

High-performance systems Reliability

Data processing pipelines
